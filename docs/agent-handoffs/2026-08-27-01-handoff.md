## The budget-allocation problem (the main thing to fix)

The Streaming Allocator (`backend/app/allocator.py`) and Policy Engine (`backend/app/policy.py`) both fully support a per-intervention incentive cost, and the reserve mechanism ("decline a mediocre case, fund a better one later" — test2108.md §13 item 2) is real and unit-tested in `backend/tests/test_allocator.py`. **But nothing in the live flow ever sets a non-zero cost**, so:

- `ProposedIntervention.incentive_amount` / `discount_pct` are always `0` (disclosed since ticket 05 / ADR-0010).
- `backend/app/lifecycle.py:148` builds `proposal = ProposedIntervention(intervention=intervention)` with no cost argument — the single live construction site.
- Result: `BudgetLedger.spent` never moves → `available` / `reserved` are flat lines on the **Reserved Budget** dashboard tab. `BudgetTimeline.tsx` currently carries an honest amber disclaimer about this.

### To make it real, roughly:

1. **Decide where an intervention's cost comes from.** Options: a fixed incentive per workflow, a discount % keyed on `customer_segment_proxy` / `failure_reason`, or a value the Decision Engine emits. This is a domain decision — likely wants an ADR and a CONTEXT.md term ("incentive", "cost model"). The evaluation harness's `fixed_rule` arm already models "flat 5% discount" (`FIXED_RULE_DISCOUNT_PCT` in `backend/app/evaluation.py`) — a starting point.
2. **Thread it through:** `run_decision_cycle` → `ProposedIntervention(incentive_amount=…, discount_pct=…)` → `validate(...)` and the `AllocationCandidate` it already builds a few lines below.
3. **Reconcile the two budgets:** `PolicyConfig.recovery_budget` and `BudgetLedger.recovery_budget` are independently-configured copies of the same number (noted in `allocator.py`'s `get_allocator()` docstring). A merchant-config object could unify them.
4. **Regenerate demo data + eval report** so the dashboard shows real movement: `cd backend && uv run python -m app.demo_seed && uv run python -m app.evaluation`. Consider seeding a case that gets declined-then-a-better-one-funded so the reserve visibly bends.
5. **Update `BudgetTimeline.tsx`** — drop/adjust the ADR-0010 disclaimer once spend is real; maybe add a visual marker where the allocator declined a case.

Related still-open gap: halted-subscription `case_value` / `avg_order_value` resolve to `0` (no Plan-amount lookup), so `escalation_value_threshold` can never fire for that workflow and that arm's NRR is structurally 0 (`run_evaluation` defaults to `FAILED_PAYMENT` for this reason).
