# Manage cases as multi-step sequences with continuous reassessment, not one-shot decisions

Every workflow discussion so far implicitly treated a case as a single decision point: an event arrives, the agent picks one intervention, done. That's thinner than what Track 3 actually asks for — "stopping rules and escalation" only mean something if a case can persist long enough to have something to stop, and the original doc calls subscription recovery "a strong agentic workflow" specifically *because* "the agent must decide what to do next and when," which presupposes more than one decision per case.

**Decision**: A Recovery Case is a persistent entity, not a single event-response pair. After each intervention, the system observes the outcome (or the absence of one) and the agent reassesses the case's recovery probability and economics before choosing what happens next — a stronger intervention, escalation to a human, or an explicit stop once further intervention is no longer economically justified. This applies to both initial workflows ([[0001]], the failed-payment and halted-subscription workflows) without requiring any new workflow type.

**Consequences**: Materially more to build than a stateless decision function — case state persists across time, something has to trigger reassessment beyond reacting to inbound webhooks (see the open question of scheduled vs. event-driven reassessment), and "stop" becomes a real, policy-bounded decision rather than a function returning. The policy parameters already agreed (`max_payment_retries`, `max_halted_recovery_attempts`, `max_interventions_per_customer`) turn out to already function as sequence-length bounds, so no rework was needed there — they were compatible with this model without anyone having called it out explicitly.
