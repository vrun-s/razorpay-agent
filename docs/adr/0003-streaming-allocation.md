# Stream case allocation online, with a reserve budget, instead of batch-optimizing offline

The doc's original flagship demo framing ("1,000 cases, ₹50,000 budget, agent allocates for max net recovery") implies solving the allocation as a single batch: see every case, then compute the globally optimal spend. That's a knapsack problem, straightforward to build, and it produces a clean "here's the optimized outcome" number — but it requires the agent to know about case #999 while deciding on case #1, which is not how revenue recovery actually operates (a payment fails, or a subscription halts, and the system must decide then, against only the budget and cases seen so far). If a judge asks whether the agent had visibility into the full case set before deciding on the first one, batch's honest answer undercuts the project's own thesis of being "a serious financial decision system," not a scored exercise.

**Decision**: Cases stream through the decision engine one at a time, in arrival order, the way they would in production. The allocator holds back a reserve against expected future cases rather than spending eagerly on whatever arrives first, so it doesn't exhaust the budget on a mediocre early case only to have no funds left for a much better one later. Separately, after the full stream has been observed, an offline-optimal allocation is computed retrospectively over the same case set purely as an evaluation baseline — reported as "the online agent captured N% of the theoretical best-possible allocation," not presented as what the agent itself did.

**Consequences**: More to build than a single batch optimizer — a pacing/reserve policy, plus the retrospective offline-optimal calculation still needs to exist anyway to produce that comparison number. In exchange, the system's operating story is honest under scrutiny, and it naturally lines up with real Razorpay API execution: each streamed decision maps to one action at the moment it's made (create a payment link, resume a charge), rather than batch's after-the-fact burst of API calls.
